### Tên Dự Án: `multi-account-video-stats`
### Kiến trúc & Cấu trúc Thư mục (Trưởng nhóm muse quyết định)
Modular Monolith tiến hóa sang Microservices, tách triệt để 3 trục: Account/Session, Proxy/Fingerprint, Dữ liệu/Stats. Core không gọi trực tiếp API nền tảng mà qua PlatformAdapter thống nhất (authenticate, list_videos, get_video_stats, refresh_token). Ưu tiên Official API, headless browser chỉ là fallback có kiểm soát. Mọi thu thập đi qua hàng đợi bất đồng bộ có idempotency, rate-limit 3 lớp và fail-closed khi proxy/session chết. Dữ liệu chuẩn hóa về một schema UnifiedVideoMetric duy nhất, lưu quan hệ ở PostgreSQL và time-series ở TimescaleDB/ClickHouse, hiển thị qua API Gateway + Dashboard realtime. Quy ước repo: src/core là dùng chung, mỗi miền (accounts, proxy, connectors, ingestion, scheduler, analytics, browser, api, web, observability, security) một thư mục riêng, scripts/data/tests/docs tách biệt.

**Cấu trúc thư mục chuẩn trên `main`:** `src/`, `src/core/`, `src/accounts/`, `src/proxy/`, `src/connectors/`, `src/ingestion/`, `src/scheduler/`, `src/analytics/`, `src/risk/`, `src/browser/`, `src/api/`, `src/web/`, `src/security/`, `src/observability/`, `src/ai/`, `scripts/`, `data/`, `data/golden/`, `tests/`, `docs/`, `docker/`

Định nghĩa entity trung tâm: Workspace, PlatformAccount, Video, VideoMetricDaily, Proxy, Task. Core chỉ làm việc với schema chung, thêm nền tảng mới chỉ cần viết adapter mới. Ban đầu triển khai monolith, tách service khi vượt ~500 account hoặc >10k video/ngày.
- **[approach_05] Connector Facebook: Graph API + Page/Video Insights** → `src/connectors/facebook_connector.py`: Dùng Facebook Graph API / Instagram Graph API qua Meta for Developers: lấy Page, video/Reels, insights (views, reach, likes, comments, shares, watch time, followers). Xử lý phân trang, token Page dài hạn, throttle + exponential backoff khi rate-limit. Map video_id gốc sang video chuẩn nội bộ, ghi rõ nguồn dữ liệu cho mỗi bản ghi. Fallback có kiểm soát bằng đọc dữ liệu công khai qua browser profile của account khi API thiếu field, có giới hạn tần suất và log nguồn.
- **[approach_09] Scheduler và hàng đợi tác vụ phân tán dưới ràng buộc quota** → `src/scheduler/task_scheduler.py`: Mọi thao tác thu thập là Job trong priority queue (Celery/RQ + Redis hoặc BullMQ) với queue riêng theo platform và loại việc: login/check-live, fetch-stats, refresh-token. Scheduler (Celery Beat/Temporal) lập lịch theo tần suất: video mới 15 phút, video cũ 6-12 giờ, account VIP ưu tiên. Ràng buộc: per-account concurrency = 1, per-proxy concurrency giới hạn, per-platform quota/ngày bằng token bucket + leaky bucket + semaphore phân tán, jitter ngẫu nhiên. Shard worker theo account_id (consistent hashing) để cùng account luôn về cùng worker, distributed lock Redis Redlock chống chạy trùng, job có lease/visibility timeout, heartbeat, retry exponential backoff tối đa 3 lần rồi vào dead-letter queue. Ưu tiên theo độ tươi dữ liệu, deadline và chi phí quota bằng weighted fair scheduling.
- **[approach_13] REST API + WebSocket Gateway làm lớp tích hợp end-to-end** → `src/api/main.py`: Backend FastAPI (hoặc NestJS) phân lớp Routers -> Service -> Adapter/Worker. API Gateway thống nhất REST/GraphQL, xác thực JWT, rate-limit theo tenant. Cung cấp REST chuẩn: /auth, /accounts (CRUD + import hàng loạt), /accounts/{id}/check-alive, /accounts/{id}/sync-videos, /accounts/{id}/assign-proxy, /videos, /videos/{id}/metrics?from&to, /proxies, /proxies/health, /proxies/import, /groups, /tags, /jobs. Phân trang cursor-based, filter platform/status/search thống nhất. WebSocket/SSE channel /ws/events đẩy sự kiện account_status_changed, sync_completed, alert. Sinh OpenAPI/Swagger tự động và SDK client TypeScript từ OpenAPI để frontend không gọi API thủ công.
- **[approach_17] Observability, cổng fail-closed và kiểm thử golden** → `src/observability/monitor.py`: Lớp observability độc lập với pipeline chính: Prometheus metrics, OpenTelemetry trace theo account_id/job_id, structured logging đã redact secret/PII, log tập trung, alerting qua Telegram/Email khi tỉ lệ lỗi tăng đột biến. Mỗi batch thu thập phải qua kiểm tra P0: schema hợp lệ, views không giảm bất thường, số lượng video khớp danh sách kỳ vọng, proxy và account đều ACTIVE; nếu thất bại thì batch bị REJECTED/NEEDS_REVIEW, không ghi đè dữ liệu cũ. Hệ thống fail-closed: proxy chết, session hết hạn hoặc API trả lỗi xác thực thì job bị REJECTED và ghi audit, không dùng proxy/session mặc định của account khác. Có bộ golden test với dữ liệu mẫu cố định cho mỗi adapter để CI phát hiện ngay khi API nền tảng đổi schema, và kill-switch dừng toàn bộ crawl khi tỉ lệ lỗi vượt ngưỡng.

Mọi chuyển trạng thái ghi audit log bất biến, không cho trạng thái mơ hồ. Hỗ trợ import/export hàng loạt CSV/Excel, gắn tag, nhóm, owner. PostgreSQL là source of truth, upsert idempotent theo khóa tự nhiên từng nền tảng, tách raw_payload JSONB có TTL khỏi dữ liệu đã chuẩn hóa.

Luôn ghi rõ dữ liệu nào từ API, dữ liệu nào từ thu thập bổ sung.
- **[approach_10] Kho dữ liệu time-series và phân tích tăng trưởng video** → `src/analytics/time_series.py`: PostgreSQL lưu dữ liệu quan hệ (account, video, user); TimescaleDB/ClickHouse lưu time-series video_metrics (time, video_id, views, likes, comments, shares) phân vùng theo platform + tháng, nén và retention tự động archive sang object storage. Tính chỉ số phái sinh bằng cửa sổ trượt: growth_rate 1h/24h, velocity views/giờ, engagement_rate = (likes+comments+shares)/views, retention proxy, top video. Phát hiện bất thường bằng z-score trên chuỗi đã khử xu hướng và Isolation Forest đa chiều để cảnh báo video tăng đột biến, tụt view hoặc dữ liệu lệch do API lỗi.
- **[approach_14] Account health score, dự đoán rủi ro khóa và xử lý checkpoint fail-closed** → `src/risk/account_health.py`: Tính Account Health Score từ tỉ lệ sync thành công, số checkpoint, captcha, rate-limit 429, proxy lỗi. Xây feature vector (tần suất request, tỷ lệ lỗi 4xx/429, số lần đổi proxy/IP, độ lệch hành vi so với baseline, tuổi tài khoản, lịch sử checkpoint) và mô hình phân loại Logistic Regression/Gradient Boosting cho risk_score 0-1 và nhãn RISK_LOW/MEDIUM/HIGH, retrain định kỳ từ dữ liệu checkpoint thực tế kèm giải thích feature quan trọng nhất. Confidence gate fail-closed: risk > 0.7 tự giảm tần suất 50%, đổi proxy sạch, tạm dừng tác vụ không thiết yếu; risk > 0.9 dừng hẳn và đưa vào NEEDS_REVIEW. Bất kỳ tín hiệu bất thường nào (login lạ, checkpoint, 2FA, đổi mật khẩu, API trả lỗi quyền) đều chuyển trạng thái ngay, dừng mọi job tự động của account đó, không thử đăng nhập lặp lại, đưa vào hàng đợi xử lý thủ công kèm bằng chứng (mã lỗi, thời điểm, proxy, screenshot/log đã che secret).
- **[approach_18] Suy luận thông minh: gợi ý nội dung, dự báo views và phân cụm video** → `src/ai/recommendation_engine.py`: Dùng dữ liệu chỉ số đã chuẩn hóa để suy luận: phân cụm video bằng TF-IDF + embedding tiêu đề/mô tả và K-Means/HDBSCAN để tìm chủ đề hiệu quả theo từng tài khoản; dự báo views 24h/7 ngày bằng mô hình chuỗi thời gian (Prophet/ARIMA hoặc LightGBM với feature thời gian + lịch sử); tối ưu thời điểm đăng bằng bài toán tìm cực đại của hàm engagement theo giờ/ngày trong tuần từ dữ liệu lịch sử. Hệ gợi ý xếp hạng video nên xem/phân tích tiếp theo bằng content-based filtering kết hợp collaborative filtering giữa các tài khoản cùng niche. Kết quả chỉ là gợi ý có độ tin cậy kèm khoảng tin cậy, không tự động đăng khi chưa được duyệt.

#### 👤 fullstack-ux (Chuyên gia Ứng dụng & Tích hợp) — nhận 5 hướng:
- **[approach_04] Proxy pool manager: sticky 1-1, chấm điểm, health-check và failover** → `src/proxy/proxy_pool_manager.py`: Quản lý pool proxy HTTP/HTTPS/SOCKS5 residential/datacenter/mobile theo quốc gia/ISP, import hàng loạt format host:port:user:pass, credential proxy cũng mã hóa. Mỗi account bind sticky 1 proxy cố định (1 account = 1 proxy + 1 fingerprint) để tránh nhảy IP gây checkpoint; chỉ rotate khi proxy chết hoặc theo lịch, chỉ chuyển sang proxy cùng geo và đưa account về warm-up. Chấm điểm động: score = w1*success_rate + w2*(1/latency_norm) + w3*stability - w4*ban_rate - w5*cost, cập nhật EWMA sau mỗi request, kết hợp consistent hashing account_id -> proxy và epsilon-greedy thử proxy mới. Health-check định kỳ latency, success-rate, IP leak/DNS leak, blacklist; proxy lỗi 3 lần liên tiếp bị quarantine, circuit-breaker + backoff hàm mũ, failover sang dự phòng cùng geo. Cấp phát bằng lease có TTL + heartbeat, ghi lịch sử account-proxy-IP để truy vết.
- **[approach_08] Pipeline ingestion chuẩn hóa đa nền tảng (Adapter + ETL + Validation)** → `src/ingestion/pipeline.py`: Pipeline 4 bước: Discover (quét video mới) -> Fetch (gọi connector qua đúng proxy của account) -> Normalize (map về UnifiedVideoMetric: video_id, platform, account_id, views, likes, comments, shares, watch_time, followers_delta, collected_at) -> Store (snapshot theo ngày, không ghi đè). Validate schema, loại giá trị âm, tăng đột biến bất hợp lý, thiếu trường bắt buộc thì đánh dấu partial/NEEDS_REVIEW thay vì điền 0 hoặc suy đoán. Deduplicate theo (account_id, platform_video_id, date bucket) với idempotency-key, xử lý video bị xóa/private, chuẩn hóa đơn vị và múi giờ UTC.
